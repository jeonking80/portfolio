# 테스트 전략과 결과

업무 규칙은 단위 테스트로, 회사 격리·동시성·불변 이력은 실제 PostgreSQL로, 업무 흐름은 실제 브라우저로 검사합니다. 한 명령으로 전부 실행합니다.

```sh
npm run verify
# 타입 검사 → 단위 → 시뮬레이터 → PostgreSQL 통합 → 운영 빌드 → 브라우저(Playwright)
```

## 층별 구성

| 층 | 도구 | 건수 | 검사 내용 |
| --- | --- | ---: | --- |
| 단위 | Vitest | 371 | 상태 전이 엔진 40개 명령의 수량 한도·상태 규칙, 권한 판정, 관제 계산, 화면 로직 |
| 시뮬레이터 | node:test | 55 | 가상 사건 생성·일정, WMS 코드를 쓰지 않는 독립 기대값 대조, 복구 판정 |
| 통합 | Vitest + PostgreSQL | 223 | RLS 회사 격리, 불변 트리거, 동시 요청과 멱등, 요청 기록, 마이그레이션 |
| 브라우저 | Playwright | 47 | 스캔 수령부터 출하까지 전체 흐름, 응답 유실 후 복구, 권한·세션 만료, 페이지 넘김 |
| **합계** | | **696** | 2026-10-22 기준 전부 통과 |

696은 자동화 실행 사례 수이며 작성 분량을 뜻하지 않습니다.

## 일부러 실패를 만드는 시험

- **응답 유실**: 브라우저에서만 응답을 버리고 서버는 커밋시킨 뒤, 다시 접속해 같은 request_id로 원래 결과를 복구하는지 확인합니다.
- **기록 실패**: 요청 기록 테이블에 예외를 일으키는 트리거를 걸어도 업무 응답은 그대로 유지되는지 확인합니다.
- **회사 경계**: 다른 회사의 ID로 조회·수정·취소를 시도해 거절되고 데이터가 바뀌지 않는지 확인합니다.
- **동시 요청**: 같은 request_id를 동시에 보내도 재고가 한 번만 바뀌는지 확인합니다.

## 측정한 개선

DB 앞에 왕복 20ms 지연을 넣은 같은 조건에서 변경 전후를 비교했습니다.

| 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 기존 홈 화면 표시 | 1.47초 | 0.84초 |
| 현장 운영 진입 | 2.64초 | 1.49초 |
| 요청당 DB 왕복 | 22~34회 | 13~21회 |

원인은 서버 지역 기본값(미국 동부), 트랜잭션마다 따로 보내던 설정 쿼리, 렌더링을 막던 외부 글꼴이었습니다.

## 하지 않은 것

- **성능 합격**: 혼잡 시험(25분 고부하 후 회복)을 여러 차례 실행했지만 목표 지연·완주 기준을 통과하지 못했고, 그 기록을 그대로 남겼습니다. 운영 환경 실측과 현장 규모 부하 검증은 하지 않았습니다.
- **장비 연동**: 실제 PDA·스캐너 SDK·라벨 프린터·택배 송장 API와 연결하지 않았습니다.
- **실제 운영**: 합성 데이터와 시험 회사로만 검증했습니다.
