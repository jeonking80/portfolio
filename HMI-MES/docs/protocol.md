# 명령·수집 계약

OPC UA 위에서 두 앱이 주고받는 메시지의 약속입니다. 모든 메시지는 Pydantic 모델로 정의했고, 모르는 필드나 모르는 종류는 오류로 처리합니다.

## 공통 규칙

- **시각:** UTC로 저장합니다. 오프셋이 없는 시각은 받지 않습니다.
- **큰 수:** 순번·수량·제어 버전 같은 64비트 정수는 JSON 문자열(`"9007199254740993"`)로 보냅니다. 브라우저의 숫자 정밀도 때문에 값이 바뀌는 것을 막기 위해서입니다.
- **ID:** 대소문자를 구분하고 공백이 없는 128자 이하 문자열입니다.

## 설비 메서드

| 메서드 | 용도 |
| --- | --- |
| SubmitCommand | 명령 제출 |
| GetCommandResult | 원래 ID로 결과 조회 |
| ReadEvents | 순번 이후의 생산·상태 사건 읽기 |
| GetRunSummary | 실행별 최종 요약 조회 |

명령 종류는 `LOAD_JOB`(작업 불러오기), `START`, `PAUSE`, `END_RUN`, `SET_PARAMETERS`(운전 중 설정 변경), `RESET_FAULT` 여섯 가지입니다.

## 명령 상태

| 상태 | 뜻 |
| --- | --- |
| ACCEPTED | PLC가 받았다는 뜻. 실행 성공이 아닙니다. |
| SUCCEEDED / REJECTED / FAILED | PLC가 확정한 결과입니다. |
| EXPIRED | 한 번도 전달되지 않았습니다. 다시 연결돼도 만료 상태로 남습니다. |
| OUTCOME_UNKNOWN | 전달됐을 수 있지만 결과를 확인하지 못했습니다. 실패의 증거가 아닙니다. |

- **결과를 기다리는 시간:** START는 10초, END_RUN은 60초를 기다립니다.
- **결과를 확인하지 못한 경우**
  - 새 ID로 다시 보내지 않습니다.
  - 원래 ID로 조회하고 설비 상태와 맞춰 봅니다.
- **같은 ID로 다시 온 요청**
  - 내용이 같으면 기존 결과를 돌려줍니다.
  - 내용이 다르면 `COMMAND_ID_CONFLICT`로 거절합니다.

## 사건 스트림

- **순번:** 수집원마다 하나의 연속된 순번 스트림이 있습니다. 순번은 1부터 시작합니다.
- **사건 단위:** 사건마다 바뀌지 않는 event_id가 있습니다.
- **원래 실행 ID:** 양품·불량·폐기 사건은 원래 execution_id가 필수입니다.
- **설비 앱 보관:** 설비 앱은 사건을 7일 보관합니다.
  - 보관 범위보다 오래된 순번을 요청하면 `RETENTION_GAP`과 정확한 누락 범위를 돌려줍니다.
  - 빈 페이지로 넘어가지 않습니다.

## ACK와 두 가지 위치

API는 수집원마다 두 위치를 따로 저장합니다.

1. **검증된 연속 위치** — 그 앞의 모든 사건이 검증·반영된 마지막 순번입니다. 빠진 사건이나 격리된 사건이 있으면 여기서 멈춥니다.
2. **최신 수신 위치** — 새 데이터를 어디까지 받았는지입니다.

- **한 트랜잭션:** 중복 제거, 실적 반영, 검증 위치 전진을 한 트랜잭션에서 처리합니다.
- **커밋 ACK:** ACK는 커밋이 끝난 뒤에만 보냅니다.
- **영구 누락:** 영구 누락이 생기면 누락 범위를 먼저 기록합니다. 관련 정산은 잠정으로 남깁니다. 수집을 계속해도 이력이 완전해진 것으로 바꾸지 않습니다.

## 실행 경계

- **최종 요약:** 설비의 최종 요약(`final: true`)은 다음 조건이 모두 맞아야 만들어집니다.
  - 상태가 종료(ENDED)
  - 재공 0
  - 종료 시각이 있음
- **MES 완료**
  - 최종 요약만으로 MES 완료가 되지는 않습니다.
  - 그 경계까지의 사건이 모두 반영되고 수량이 맞아야 완료입니다.
  - 미해결 누락이나 충돌이 없어야 다음 작업을 연결할 수 있습니다.
